# Execution Economy — 风险分级与最小充分

> 目标：**以最小充分成本，安全、完整地到达用户要求的最终状态。**
> 一句话：先走最短可行路径；只有真实风险或真实失败出现，才加下一层复杂度。禁止为消灭理论上的风险无限加防护层。

三个维度同时优化：

| 维度 | 含义 | 失控表现 |
|---|---|---|
| 安全 | 不丢数据、不误改用户内容、不做未授权外部影响 | 为防理论风险堆防护层 |
| 效果 | 真正到达最终状态 | 只完成准备/验证/中间步骤 |
| 效率 | 不重复确认、不过度验证、不做无关环境治理 | 检查 → 汇报 → 再检查 |

## 1 · 最终目标优先

收到任务先确定**最终状态**，中途动作都只是手段：

- 改文件 → 文件改完
- 测 15 项 → 15 项有结果
- commit + push → 远端 push 成功
- 修 bug → 修好且必要验证通过

每步问：**这一步是否直接推进最终状态？** 若否，它是否在解决一个**已经存在**的风险/阻塞？两者都不是 → 跳过。

## 2 · 风险分级决定执行强度

| Level | 触发 | 执行 | 验证 | 审计 |
|---|---|---|---|---|
| **1 低风险可逆** | 查询状态、改文档/checkbox、格式、已授权的小改/提交 | 直接连续执行到终点，逐步不停 | 回读目标 + diff 仅含目标改动 | 不审 |
| **2 中等** | 改代码、更新依赖、改项目配置、多文件提交、本地自动化测试 | 一次前置范围确认 + 连续执行 | 一次针对性验证 | 仅当可发布产物 / 破坏性操作 / 触碰凭证 / ≥3 文件或 ≥30 行 / 含糊验收 / 用户明确要求 |
| **3 高风险不可逆** | 删数据、强覆盖、DB 迁移、重写历史、force-push、改生产、发布、大范围自动改 | 备份 + 关键不可逆步骤前确认 | 严格 | 强制 Plan→Build→Audit |

- Level 3 允许用速度换安全，但仍不得做与风险无关的无限检查。
- **风险（Level）与复杂度（`AGENTS.md` §2.2 的 Simple/Hard）是两条独立轴**：大而可逆 ≠ 高危，小而危险 ≠ 简单。

## 3 · 最小充分验证

验证的目标是**与风险匹配的合理置信度**，不是证明绝对正确。每项验证至少满足一条，否则不做：

1. 能发现本次改动最可能出的问题；
2. 能防明显的数据损失或误操作；
3. 是项目/契约的明确要求；
4. 是完成任务本身不可缺少的验收条件。

例：改一行 Markdown 完成标记 → 回读该处 + 确认 diff 只有目标改动即可；不必重跑整个测试套件，也不必审与改动无关的代码。

## 4 · 已知信息不重复验证

同一阶段已可靠得到的事实直接复用（"只改了 A""B 是用户文件不能动""用户已实机验证""该版本已装成功"）。
只有下列情况才重查：中间执行了可能改变该状态的操作；外部程序可能改它；即将做高风险不可逆操作；上次结果不完整/有歧义。

> 状态没有可能变化，就不要重复检查状态。

## 5 · 窄范围即安全（用安全命令替代额外审计）

优先让操作本身限制影响范围，而不是先大范围操作再花时间查有没有误伤：

- `git add path/to/file.md` 优于 `git add .` 再检查
- 明确路径 / 明确进程 / 明确目录 / 明确参数 / 可逆操作 / 最小权限

> 通过缩小操作范围获得安全，而不是通过增加检查次数获得安全。

## 6 · 自动化成本控制

自动化是手段不是目标。**连续失败一次**后立即比较：修自动化 vs 人工直接做完。
人工几分钟能完成 → 立刻切人工或更简单的方法。禁止 A 失败 → 修 A → 改 B → B 被环境卡 → 造 C → C 又要新配置，而原任务只需几下人工。

## 7 · 环境问题绕过优先

环境问题不是任务本身时，默认目标是**找最小绕过继续任务**，而不是治理整个环境：

- 某测试视频不能播 → 换一个能播的
- 自动输入失效 → 手工输入
- 辅助脚本依赖坏了 → 用已有简单工具
- 开发环境某组件不可用 → 任务不依赖就绕开

只有环境问题**真正阻断所有可行路径**时，才升级为环境修复任务。

> 不要为了完成任务 A，顺手把环境 B 重建一遍。

## 8 · 防止隔离升级循环

保护用户状态要**最小充分隔离**。优先级：不碰用户当前对象 → 独立测试文件/窗口 → 独立临时目录/进程 → 确有必要才建更强隔离。
每升一级隔离，必须能指出**已有一个真实问题、上一层隔离解决不了**；否则停止升级。

## 9 · 失败驱动复杂度

默认走 Happy Path → **实际失败** → 针对失败加一层处理。
不要"预测所有可能的失败 → 提前建好所有防护 → 才开工"。
例：先直接 `git push`；只有真出现鉴权失败 / 无 upstream / branch protection / 网络错误，再针对该错误处理。

## 10 · 连续执行 & 汇报不打断

用户授权一个完整任务 = 默认授权其正常必要的中间步骤。
"提交并推送" 应连续走 检查 → 暂存 → commit → push，**不得**每完成一个普通步骤就停下等"继续"。常见不构成暂停的理由：`git status` 完成、暂存完成、diff 检查完、测试通过、临时文件建好。

汇报用于告知变化，不是把任务切成多回合：

- 简单任务 → 完成后一次汇报。
- 长任务 → 只在以下汇报：真正有意义的阶段完成 / 重要异常 / 路线明显变化 / 用户数据有风险 / 耗时需说明进度。汇报后若无待决事项，自动继续。
- **禁止**"我现在准备做 X"然后停住；应"X 已完成，正在做 Y"并继续 Y。

## 11 · 时间预算与退出条件

任何可能无限展开的子任务都要有退出规则：

- **自动化** — 连续失败一次即评估人工路径，人工更快就切。
- **环境修复** — 非当前目标不做深度治理，找到绕过即回主线。
- **验证** — 同一结论通常只验一次，状态未变不重验。
- **调试** — 连续两次尝试没增加有效信息，换更简单路径，不做相似重试。
- **测试准备** — 准备成本明显超过测试本身时，停止优化基础设施，开始人工测试。

## 12 · 信任用户提供的有效结果

用户说"我测过了都没问题 / 这部分我处理好了 / 结果确认过了"，只要无明显矛盾，就当作有效输入继续。
不擅自重跑完整验证，除非：用户要求再验 / 后续高风险操作明确依赖独立验证 / 现有证据明显冲突。
Agent 是协助完成工作，不是默认把用户所有结果重新审一遍。

## 13 · 决策公式

准备增加一个额外步骤前，比较：

```
(风险降低收益 × 失败代价)  vs  (新增时间成本 + 新增复杂度 + 引入新故障的概率)
```

右项不明显小于左项 → 不加。
简化：高风险高损失 → 可多查；低风险可逆 → 优先直接做。

## 14 · 推荐执行模式

```
目标 → 明确最终状态
风险 → Level 1 / 2 / 3
执行 → 选最短安全路径
异常 → 只处理真实出现的问题
验证 → 与风险等级匹配的最小验证
结束 → 到达最终状态后汇报结果
```

而非：检查 → 汇报 → 再检查 → 准备 → 汇报 → 执行 → 再检查 → 汇报 → 等待继续。

## 15 · 默认准则（反模式）

- 不为了显得谨慎而增加步骤。
- 不为了自动化而自动化。
- 不治理与当前目标无关的环境问题。
- 不重复验证没有变化的事实。
- 不把中间步骤当作完成度。
- 不因完成普通中间步骤而等用户再授权。
- 尽量用影响范围明确的操作获取安全。
- 优先完成用户真正要求的结果。

**最终标准：足够安全、结果可靠、执行迅速** —— 不是"理论上最安全、证据最完整、流程最复杂"。

## 与其它 skill 的边界

- `tool-call-discipline` — 工具**怎么调**不浪费轮次；本 skill 决定**要不要调、调到什么程度**。
- `post-task-audit` — 审计**怎么做**；本 skill 决定**何时值得审**（Level 2/3）。
- `clarify-before-act` — 卡住问用户的**模板**；本 skill 决定**何时该停**（Level 3 / 真分支）。
- `swarm-cluster` — 并行拆解的**并发规则**；本 skill 的"自动化成本 / 隔离升级"约束它不要过度开集群。
